# Spec: Каркас проекта на MVC-архитектуре

**Статус:** done
**Версия:** 1.0
**Дата:** 2026-11-25
**Автор:** DuXae

## 1. Проблема

Репозиторий `project-A` содержит только SDD-шаблоны. Нет ни кода, ни структуры,
на которую можно опереться при разработке первой реальной фичи. Каждая новая
фича рискует получить собственную самодельную структуру.

## 2. Цель

После внедрения команда сможет добавлять новые сущности и эндпоинты по единому
шаблону: контроллер → сервис → репозиторий → БД, с валидацией, обработкой ошибок
и тестами, чтобы каждая фича была предсказуемой и проверяемой.

## 3. Пользователи и сценарии

### Сценарий 1: Разработчик добавляет новую сущность
- **Дано:** каркас MVC в `main`, локально поднята PostgreSQL
- **Когда:** разработчик создаёт сущность, репозиторий, сервис и контроллер
  по образцу демонстрационной сущности `Note`
- **Тогда:** эндпоинты `/api/v1/<entities>` работают, ошибки валидации
  возвращаются в едином формате, тесты проходят

### Сценарий 2: Клиент вызывает API
- **Дано:** приложение запущено
- **Когда:** клиент обращается к `/api/v1/notes`
- **Тогда:** получает JSON-коллекцию с пагинацией либо корректную ошибку
  (400/404/500) в едином формате

### Сценарий 3: Развёртывание
- **Дано:** чистая база
- **Когда:** приложение стартует
- **Тогда:** схема БД создаётся/обновляется миграциями автоматически,
  приложение отвечает на `/actuator/health`

## 4. Функциональные требования

| ID   | Требование                                                                 | Приоритет |
|------|----------------------------------------------------------------------------|-----------|
| FR-1 | Приложение на Java 21 + Spring Boot собирается Maven и запускается одной командой | must |
| FR-2 | Слои разделены: web (контроллеры + DTO) → service → repository → domain    | must      |
| FR-3 | Демонстрационная сущность `Note` с CRUD: list (пагинация), get, create, update, delete | must |
| FR-4 | Валидация входящих данных (Jakarta Bean Validation), ошибки — 400          | must      |
| FR-5 | Единый формат ошибок API (code, message, details, timestamp)               | must      |
| FR-6 | Схема БД управляется миграциями Flyway                                    | must      |
| FR-7 | Health-check эндпоинт `/actuator/health`                                  | should    |
| FR-8 | Конфигурация через переменные окружения, секреты не в репозитории          | must      |

## 5. Нефункциональные требования

| ID    | Требование                                                        |
|-------|-------------------------------------------------------------------|
| NFR-1 | Слои не протекают: контроллер не работает с JPA-сущностями напрямую |
| NFR-2 | Покрытие тестами слоя web и service для CRUD-сценариев             |
| NFR-3 | Время старта приложения < 10 c на локальной машине                 |
| NFR-4 | Код соответствует единому стилю форматирования (spotless/checkstyle опционально) |

## 6. Критерии приёмки

- [x] AC-1 (FR-1): `mvnw spring-boot:run` поднимает приложение на :8080
- [x] AC-2 (FR-2): структура пакетов `web`/`service`/`repository`/`domain` присутствует и не смешивается
- [x] AC-3 (FR-3): все пять CRUD-операций по `Note` работают через HTTP
- [x] AC-4 (FR-4, FR-5): POST с пустым `title` возвращает 400 и тело `ErrorResponse`
- [x] AC-5 (FR-6): на чистой БД Flyway создаёт таблицу `notes`
- [x] AC-6 (FR-7): `GET /actuator/health` возвращает `{"status":"UP"}`
- [x] AC-7 (NFR-2): `mvnw test` проходит, тесты контроллера и сервиса зелёные
- [x] AC-8 (FR-8): `application.yml` не содержит паролей, только `${ENV_VAR:default}`

## 7. Вне скоупа

- Аутентификация и авторизация (появится отдельной спекой)
- HTML-шаблоны и server-side rendering — по решению заказчика только JSON API
- Docker/docker-compose (Docker не установлен), CI-пайплайн
- Кэширование, очереди, интеграции
